## 2x1 打卡按钮内边距对称化（已实现）
- 需求：按钮内部「上/下班卡」文字左内边距要与右侧一样（之前左贴边 0、右 2dp），且保留时间文字与按钮的距离。
- 坑：Glance 的 Box 外层 `.padding(start)` 与内层 `.padding(start)` 会叠加（背景框把外边距算进框内），导致左=8dp 右=2dp 不对称。修法：外层 start 归 0，内层 start=2dp、end=2dp，左右对称。时间文字 defaultWeight() 保留（与按钮 gap=0，用户认可）。
- 验证范式：装后用 `adb shell uiautomator dump /sdcard/widget_dump.xml` + pull + Python 解析 parent map，量 box 与 text 的 bounds 差值，直接计算内部左右内边距像素。设备密度 density≈3(xxxhdpi)，2dp=6px。
- 字号上限结论：时间串 "HH:MM – HH:MM"(13字符) 当前 12.sp 实测占满整行剩余宽度(~273px≈91dp)，12.sp 即天花板；13.sp+ 裁切末尾。缩短格式(去空格 "08:30–20:30")可放到 ~14.sp。
- 方案A已落地(用户确认)：ScheduleGlanceWidget 第二行时间 Text 由 "$displayStart – $displayEnd"(含空格) 改为 "$displayStart–$displayEnd"(去空格) + fontSize 12→14.sp；实测 "08:30–20:30" 14.sp 宽 273px=91dp 正好填满可用宽、右缘贴按钮(gap=0)、未裁切、未重叠。时间左对齐/按钮右对齐/中间弹性留白布局不变(时间 defaultWeight 顶满、按钮 wrap_content 居右)。布局意图：距离无所谓，只要时间不裁切。

## 2x1 打卡按钮高度最大化（已实现）
- 需求：第一行/第三行位置不变，打卡按钮高度做到最大(仅变高、宽度/位置不变)，不遮挡上/下行。
- 机制：原三行均 defaultWeight() 等分(各 1/3)，按钮被压在中间 1/3。改成"上下两行 wrap content + 中间行独吞剩余 + 按钮 fillMaxHeight"：第一行 Row 去 defaultWeight()(贴顶,占内容高)、第三行 Box 去 defaultWeight()(贴底,占内容高)、第二行 Row 保留 defaultWeight()(吃满"第一行底→第三行顶"全部剩余空间)、打卡按钮 Box 加 .fillMaxHeight()(撑满第二行高)。
- 实测(dump5)：按钮 box h 62px→120px(≈20.7dp→40dp,翻倍)；宽度 111px(37dp)不变；footer 顶边(y=395)=按钮底边(y=395)紧贴不重叠；第一行仍在顶部未被触碰。密度≈3,2dp=6px。
- 注意：改后第一行会从"1/3区居中"变为"贴顶"、第三行贴底——仍固定在顶/底，这是让按钮最大化且不遮挡的唯一方式。

## 2x1 刷新提示修复 + 三组件图标水平对齐 + 刷新功能端到端验证（已实现）
- 问题1(2x1 刷新不弹提示)：根因是 RefreshScheduleWidgetAction 直接调 `Toast.makeText().show()`，而 ActionCallback.onAction 是 suspend 协程、未必在主线程，Toast 抛异常被 Glance 吞掉。修法：包进 `Handler(Looper.getMainLooper()).post { Toast... }`，与 3x3/3x4 的 RefreshWidgetAction 完全一致。两者 toast 文本均为"刷新成功"(已一致)。
- 问题2(刷新图标偏下、与设置图标不在同一水平线)：根因是 ⚙(U+2699) 与 ↻(U+21BB) 符号字形在 em box 内垂直基线不一致，同字号同 padding 仍视觉错位。修法：两图标均用固定尺寸、内容居中的 Box 包裹(2x1 size(18.dp)、日历 size(20.dp)，contentAlignment=Center)，并加文本呈现选择符 \uFE0E 强制单色文本字形、基线一致；这样同一 Row(CenterVertically) 内两 Box 同高且居中 → 图标同一水平线。改 CalendarGlanceWidget(3x3/3x4 共用一处) + ScheduleGlanceWidget(2x1) 两处。
- 验证(端到端真实点击)：装带临时 Log.d("WIDGET_DBG",...) 的包 → 唤醒解锁设备 → uiautomator dump 取桌面 ↻ 屏幕坐标 → `adb shell input tap` 分别点 2x1 与日历的 ↻ → logcat 抓到 "refresh 2x1 fired" 与 "refresh calendar fired"，确认三组件手动刷新 ActionCallback 均真实触发(3x3/3x4 共用 CalendarGlanceWidget+RefreshWidgetAction，故两者均覆盖)。验证后移除临时日志与 import，重新干净构建安装。
- 注意：设备会休眠进入锁屏(OPPO keyguard)，dump 抓不到桌面组件；测试前先 `adb shell input keyevent KEYCODE_WAKEUP` + `wm dismiss-keyguard`，且每次 dump 后组件坐标可能变化，需按最新 dump 重新算中心再 tap。
- 关键经验：Glance widget 的 ActionCallback 里弹 Toast 必须切主线程 Handler；符号图标垂直对齐用"固定高 Box + contentAlignment Center + \uFE0E"而非仅靠同 padding。

## 16:00 会话：架构升级为「全局数据变更信号自动同步」（回答用户稳定性质疑）
- 用户质疑：改班次后点刷新仍不立即更新；问方案是否最稳定、是否受系统桌面约束、能否点刷即刷。
- 排查结论：刷新按钮机制本身 100% 正常（多次真机验证：点刷新→读DB→立即渲染，夜3→夜5→值3→值5 全对）；"不更新"的根因是 App 端很多写库路径（batchApplyShift/详情保存/班次编辑）不触发组件同步，且原 ViewModel 的指纹同步只在日历页加载时跑。
- 升级：①ShiftRepository/ShiftStatusRepository 新增 changeSignal（与 ScheduleRepository.refreshSignal 同类）；②ScheduleApp.onCreate 起全局协程 merge 三个信号 debounce(400ms)→syncAllWidgets，任何落库修改组件 400ms 内自动更新（改完班次不用点刷新）；③冷启动(delay 1s)同步一次；④syncAllWidgets 加 Mutex 串行化（防打卡直调+信号双路并发渲染竞争，OPPO 桌面会丢弃同窗口期多次 update）；⑤打卡动作移除直调 refreshWidgets（依赖信号单次更新）；⑥refreshCalendarWidgets 无存储数据时默认当前月（新组件初始化）。

- 关键经验：Glance 组件更新链路=App→AppWidgetService→桌面渲染，OEM 桌面在组件交互瞬间可能丢更新；手动刷新按钮永远是最可靠的兜底。

## 16:15 会话：找到真正根因——「双路更新被桌面丢弃」（单路更新已修复并验证）
- 用户新症状：①改班次/改显示模式后点刷新仍不立即生效，要等一会再刷才行；②App 内改班次回桌面组件不更新，只有冷启动才刷新。
- 决定性实验：punch 直调+信号双路时（15:41/15:45）组件不渲染；改造成"只有信号单路"后（16:03/16:09 两次），点上班卡→仅一次信号同步→组件**未点刷新**自动变为下班卡 ✓。
- 结论：数据**写入是即时的**（用户假设不成立），真正原因是每次变更产生**双路 update**（ViewModel 指纹同步 150ms + 全局信号 400ms；打卡是直调+信号），OPPO/ColorOS 桌面丢弃同窗口期的多次 update；冷启动时的单次同步才能生效 → 用户观察到"只有冷启动才刷新"。
- 修复：①CalendarViewModel 删除 widgetFp/lastWidgetSyncFp/widgetSyncJob 指纹同步块（改为注释说明由全局信号统一驱动）；②删除 App 内打卡的 syncClockInWidget() 直调（clockIn/clockOut）；③上一轮已删打卡按钮直调；④WidgetConfigActivity.finishConfig 更新改为主线程 Handler postDelayed 1.2s 单次（避开 Activity 关闭瞬间桌面切换窗口期，防丢）。
- 最终架构（每处变更恰一次 update）：数据变更→仓库信号→ScheduleApp 全局收集(400ms)→syncAllWidgets(互斥锁串行)→更新全部组件；手动刷新/冷启动同步/WorkManager 15min/配置页延迟更新为兜底。
- 遗留：若个别 OEM 桌面仍丢更新，可再尝试打卡后 Handler postDelayed 500ms 延迟补一次 update；或组件侧改用 actionRunCallback 传参不依赖读取时序。

## 16:40 会话：定位「打卡后组件不渲染 + toast 不弹」——OEM 桌面交互窗口期丢弃更新
- 诊断（WIDGET_DBG 日志）：打卡动作全链路正常（start→saved→posting toast→信号同步400ms触发），但组件不重绘、toast 不可见；uiautomator 在该 OPPO 设备上看不到任何 toast（刷新 toast 也看不到），toast 验证方法失明。
- 关键实验：打卡后信号同步(+400ms)的 update 被桌面丢弃；24s 后手动刷新同一 update 正常渲染 → 「组件交互瞬间附近的更新被 OPPO 桌面丢弃，稍后更新可生效」。
- 修复（分层兜底）：①打卡动作加 widgetFallbackScope 延迟 1.2s 单路 syncAllWidgets（避开交互窗口期）；②打卡 toast 改 postDelayed 500ms + applicationContext；③后台钩子改两段式（1.5s+4s，覆盖桌面稳定时间差异）；④仓库信号改 MutableSharedFlow(replay=1) 修复冷启动时收集器未订阅导致的信号丢失；⑤手动刷新/冷启动同步/WorkManager 15min 保留为最终兜底。
- 验证：回桌面后 1.5s+4s 两次同步均触发，组件渲染为最新数据 ✓；手动刷新渲染 ✓。
- 注意：用户滑动关闭(swipe-away)App 后进程被杀，任何后台机制（含 WorkManager）都无法更新组件（Android stopped-state 限制），只有再点组件（刷新按钮/冷启动）才能更新——这是平台约束，需向用户说明。
